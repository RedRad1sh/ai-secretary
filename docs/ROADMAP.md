## Приоритет 0 — доступ для нескольких пользователей

- [x] Изолированы настройки, события, история, `/undo`, статистика и напоминания.
- [x] Аудит изоляции (27.09, issue #3): `tests/test_multuser_security.py`

- [x] Обработка только в личном чате; общий Google OAuth не используется.
- [x] Ручная выдача платных возможностей с проверкой кнопок подтверждения.
- [ ] В рабочем окружении заполнить общий список, в платном пока оставить только

### Политика доступа (заготовка оплаты)

| Общий whitelist: этапы 0–2 | Платный whitelist: функции этапа 4 |
|---|---|
| Одиночное событие из текста, голоса, пересылки | Несколько событий за сообщение |
| Предпросмотр, уточнение, .ics | Повторяющиеся события и их напоминания |
| `/list`, `/undo`, `/settings`, `/cancel` | `/today`, `/tomorrow`, `/stats` |
| Обычные напоминания | Перенос/отмена текстом, OCR фото |

Доступ — через `Config.is_paid`; интеграции с оплатой пока нет. Подписки, чеки,
срок действия, квоты, платёжные webhook — следующий самостоятельный этап.
Простые признаки повторов/пакета проверяются до LLM; найденные AI расширенные
события проверяются перед показом и ещё раз при подтверждении. Поэтому неявное
сложное сообщение всё ещё может потратить один базовый LLM-запрос.

**Уточнение к правилу «всё после этапа 2 платное»:** этап 3 — инфраструктура.
Изоляция, сохранность данных и доставка базовых напоминаний нужны всем; их нельзя
отключать бесплатным пользователям. Пользовательские функции этапа 4 закрыты.
Голос сохранён в базовом доступе как уже существовавшая функция MVP.

## Этап 1 — стабилизация

- [x] Ограничен общий бюджет OpenAI-compatible LLM: 35 с по умолчанию, включая
  лимитер, повторы и ожидания. Затем локальный разбор с предупреждением в карточке.
- [x] Начальный/предельный бюджет 4096/8192 токенов; рост на `length` не расходует
  счётчик сетевых ретраев, для каждой fallback-модели бюджет начинается заново.
- [x] `length` проверяется до ретрая пустого content. Совместимость JSON хранится
  отдельно для каждой модели; все физические запросы проходят лимитер.
- [x] Диапазоны «с 10:00 до 11:30» и через полночь не разбиваются на два события.
- [x] AI-события без даты больше не получают случайную дату соседнего события.
- [x] Исправлено уточнение даты для списка черновиков (раньше `draft=None` приводил
  к ошибке). Одна дата уточнения применяется ко всем черновикам без даты.
- [x] Бэкап SQLite через backup API: `scripts/backup.py`.
- [ ] Реальный прогон доставки напоминаний и восстановление из бэкапа на хосте.

## Этап 3 — надёжность 24/7

Выбран поддерживаемый сейчас вариант: **один polling-процесс Docker/VDS**,
`restart: unless-stopped`, постоянный volume `./data`. Выбор/аренда сервера и
внесение секретов не выполнялись из этой сессии.

- [x] Существующий Docker restart/volume сохранён, OCR включён в образ.
- [x] После ошибки Telegram напоминание остаётся неотправленным для следующего
  прогона, а не теряется. Заголовок экранируется для Telegram HTML.
- [x] У каждого разрешённого пользователя свой адресат и собственная БД.
- [x] Повторы: первое подходящее вхождение включено, горизонт из 8 напоминаний
  автоматически пополняется; повторное пополнение не добавляет те же записи.
- [x] RRULE в списках, напоминаниях и .ics согласован через python-dateutil:
  начало недели/INTERVAL; 31-е число пропускает короткий месяц, а не сдвигается.
- [x] При старте polling не выбрасывает накопившиеся сообщения.
- [x] Исправлена потеря ссылки `_db` в инициализации webhook-адаптера.
- [ ] На хосте: cron/Task Scheduler для бэкапов, защищённая копия ключей,
  восстановление тестовой копии, проверка после перезапуска машины.
- [ ] Приёмка: 7 дней без ручного вмешательства, тест напоминания после 3 ч тишины.

**Ограничения:** FSM хранится в памяти — неподтверждённые карточки нужно отправить
заново после рестарта. Доставка at-least-once: падение между Telegram send и записью
в БД может дать дубль. Несколько одновременно работающих процессов не поддержаны.
YC Functions с `/tmp` нельзя считать надёжным хранилищем; YDB/другой внешний backend
отложен как альтернативный деплой, не отмечен выполненным. Требование «ответ ≤5 с»
для бесплатных LLM не гарантируется и не является выполненным критерием.

## Плановые запросы, серии событий (issue #13)

Боевой лог 28.09.2026: запрос «план тренировок на неделю, 12 событий» — бот
тихо выдумал время 08:00–09:00 и раскол «утро/вечер»; «всю неделю» свернул
до 6 дней; предпросмотр из 12 карточек был нечитаемым.

- [x] System prompt (`bot/services/extractor.py`): правила для плановых
  запросов — количество и содержание строго из запроса пользователя,
  время/длительность/раскладка не выдумываются; любой дефолт модель обязана
  перечислить в новом поле `assumptions`.
- [x] Каждое допущение маркируется в карточке/предпросмотре:
  «⚠️ время не было указано — поставил дефолт 08:00–09:00» (и т.п.:
  длительность, дни недели, раскол).
- [x] Без тихих дефолтов: время и длительность без значения из текста
  получают дефолт системы (10:00, 60 мин) с явной пометкой; если во всём
  запросе не было ни одного времени, любое время события помечается
  страховочно, даже когда модель «забыла» assumptions.
- [x] Компактный предпросмотр серий (≥3 похожих = одинаковые заголовок и
  описание): один блок «период | время | описание | N событий + флаги»
  вместо N карточек, кнопка «Создать все?» остаётся.
- [x] Тесты: `tests/test_planned_requests.py` (FakeLLM-сценарии, 20 проверок:
  дефолтные времена, маркеры, компактный вид, экранирование).

**Ограничения:** вариант «краткий уточняющий вопрос вместо генерации» не
реализован (критерий допускает «либо/либо») — выбрана генерация с явными
дефолтами и пометками. Похожесть серий — по заголовку и описанию; события
с RRULE и смешанные пакеты показываются карточками. Локальный (офлайн)
парсер продолжает маркировать допущения только общим предупреждением
`extraction_note`. Страховка кода покрывает выдуманное время; дни недели и
«раскол» зависят от честности модели (правило в prompt + поле assumptions).
