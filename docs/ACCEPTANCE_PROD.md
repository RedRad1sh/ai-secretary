# Чек-лист боевой приёмки — черновик v1 (28.09.2026)

**Исполняемая версия с галочками и счётчиком прогресса — [issue #11 «Боевая приёмка: чек-лист (боевой хост)»](https://github.com/RedRad1sh/ai-secretary/issues/11).**
Галочки ставятся там; каждый проход по хосту дописывает строку в «Журнал проходов» ниже (коммитом — история остаётся в репозитории).

Приёмка **на боевом хосте** (Docker/VDS, один экземпляр polling, постоянный `./data`).
Кодовая часть всех пунктов покрыта офлайн-тестами в репозитории (ссылки в `[тест]`);
здесь проверяется работа на реальных данных/хосте, которую из сессии выполнить нельзя.

Как пользоваться: пункты идут блоками; в каждом — действие → **ожидаемый результат**.
Отмечайте ☑/☒, новые дефекты — отдельным issue со ссылкой на пункт.
Определение готовности: все пункты ☑ без открытых дефектов → закрыть #2, #4, #5, #6.

Состав: владелец (paid), второй пользователь whitelist (free), при возможности —
человек «с улицы» (не в whitelist).

## 0. Подготовка

- [ ] 0.1 Хост: VDS с постоянным диском; Docker + docker compose; порт наружу не нужен (polling).
- [ ] 0.2 `.env` заполнен по `.env.example`: `BOT_TOKEN`, `ALLOWED_USER_ID` (влад.), `ALLOWED_USER_IDS` (всех), `PAID_USER_IDS` (**только свой пользовательский ID**), LLM-тройка (`LLM_API_URL`/`LLM_API_KEY`/`LLM_MODEL`), часовой пояс по умолчанию.
- [ ] 0.3 `ENCRYPTION_KEY`/`secret.key` сгенерирован и хранится только на хосте; бэкапится (блок 5).
- [ ] 0.4 LLM проверен: `python scripts/test_llm.py` (в Docker: `docker compose exec bot python scripts/test_llm.py`).

## 1. Сборка и запуск (issue #6, пункт 6)

- [ ] 1.1 `docker compose build` **с нуля** (без кэша): сборка проходит; в образе есть `tesseract` с языками rus+eng (`docker compose exec bot tesseract --list-langs`).
- [ ] 1.2 `docker compose up -d`; в логах: бот запущен, polling, ошибок нет.
- [ ] 1.3 `docker compose restart bot` (или перезагрузка машины) → бот поднимается сам (`restart: unless-stopped`), `/start` отвечает.
- [ ] 1.4 Данных нет «в воздухе»: все файлы (БД, ключ, логи) в `./data`; после пересоздания контейнера `/list` прежний.

## 2. Базовые сценарии (этапы 1–2)

- [ ] 2.1 Текст: «встреча с Иваном завтра в 15:00 в офисе» → карточка предпросмотра → ✅ Создать → приходит **.ics** + (если настроена) ссылка на Google Calendar.
- [ ] 2.2 Голосовое сообщение с датой/временем → транскрипт в карточке → .ics.
- [ ] 2.3 Пересланное сообщение-афиша → .ics.
- [ ] 2.4 `/list` — 10 последних событий со ссылками; `/undo` — последнее убрано (и его напоминание отменено — см. 4.5).
- [ ] 2.5 `/settings`: часовой пояс меняется (валидный и **невалидный** — отказ), интервал напоминаний 10/30/60/off.
- [ ] 2.6 «Кривые» заголовки: создайте событие с заголовком вида `<b>тест</b> & "кавычки"` (или пришлите такой текст) → в `/list` и карточках показывается **как текст**, без поломки HTML (issue #8, production-приёмка).
- [ ] 2.7 Дата не распознана → бот просит уточнить; «15.10.2026 14:00» подставляется без вопросов.

## 3. Качество .ics в реальном календаре

- [ ] 3.1 Импортируйте обычный .ics в Google Calendar (кнопка «Открыть в Google Календаре» и вручную) → событие с правильным датой/временем (МСК), длительностью.
- [ ] 3.2 All-day событие («завтра весь день праздник») → в календаре день целиком, без времени.
- [ ] 3.3 .ics повторяющегося события → в календаре серия по RRULE (проверить 2–3 вхождения).
- [ ] 3.4 Проверьте второй календарь (Apple/Outlook/Yandex): .ics открывается, TZID Moscow учтён.

## 4. Этап 4: пакеты, повторы, управление, напоминания

- [ ] 4.1 Одно сообщение с двумя событиями («10:00 планёрка, а в 15:00 врач») → общий предпросмотр «Создать все (2)» → **два .ics**.
- [ ] 4.2 «каждую пятницу в 18:30 созвон» → карточка с 🔁 → .ics с `RRULE:FREQ=WEEKLY;BYDAY=FR`.
- [ ] 4.3 `/today` и `/tomorrow` с повторяющимся событием → вхождение показывается в нужный день (с 🔁).
- [ ] 4.4 Перенос текстом одиночного: «перенеси встречу на 10:00» → подтверждение → время меняется, **длительность сохраняется**.
- [ ] 4.4а Перенос **повторяющегося**: «перенеси созвон на 19:00» → серия на новом времени (проверить по будущим напоминаниям/карточкам), «перенеси созвон на <dd.mm> в 18:30» → серия следует за новым днём недели (RRULE обновлён).
- [ ] 4.4б Несколько похожих событий → бот спрашивает «какое именно?» → выбор по кнопке работает (не молчит).
- [ ] 4.5 Отмена текстом: «отмени <событие>» → подтверждение → «🗑 Отменил»; **напоминание о нём не пришло** (проверить по прошлому опыту 4.6).
- [ ] 4.6 Напоминания: создайте событие через 20–40 минут с интервалом 10 мин → за 10 минут пришло «⏰ Через 10 мин…». Повторите на free-пользователе (базовые напоминания — всем разрешённым).
- [ ] 4.7 Напоминание **не** уходит повторно после доставки; после отмены события — не уходит (см. 4.5).
- [ ] 4.8 `/stats` — события/напоминания/сбои считает; размер БД — своей (у второго пользователя — своей).
- [ ] 4.9 Плановый запрос (issue #13): «сделай план тренировок на неделю, 5 событий» (без времени в запросе) → события получили дефолтное время, в предпросмотре **маркеры допущений** «⚠️ время не было указано — поставил дефолт …» (и о длительности) — тихих дефолтов нет [тест: tests/test_planned_requests.py].
- [ ] 4.10 Серия ≥3 похожих событий (issue #13) → **один компактный блок** «период | время | описание | N событий + флаги» вместо N карточек, кнопка «Создать все (N)» работает, создаётся ровно N событий [тест: tests/test_planned_requests.py].

## 5. OCR на реальных фото (issue #6, пункт 5)

- [ ] 5.1 Реальное фото афиши/заметки (рус+англ, нормальный свет) → текст распознан, предпросмотр с **правильной датой/повтором**, .ics.
- [ ] 5.2 Фото с мелким/кривым текстом → либо точное распознавание, либо бот вежливо просит чётче (без падения).
- [ ] 5.3 Фото >5 МБ → отказ «больше 5 МБ».
- [ ] 5.4 PDF/видео → отказ «пришлите как фото».
- [ ] 5.5 Платному — фото → PAID_NOTICE, распознавание не выполняется (проверить в логах: OCR не вызывался).

## 6. Многопользовательская изоляция (на живых аккаунтах)

- [ ] 6.1 Free-пользователь: одиночное событие, текст/голос/пересылка, .ics, `/list`, `/undo` — работают.
- [ ] 6.2 Free-пользователю: пакет/повтор/`/today`/`/tomorrow`/OCR → PAID_NOTICE.
- [ ] 6.3 Данные не пересекаются: `/list` у каждого — только своё; событие, созданное вторым, не видно у владельца.
- [ ] 6.4 «Чужой» callback: открыть ссылку/кнопку от чужого предпросмотра (или подменить `callback_data`) → «не ваш контекст», чужое не создано/не удалено.
- [ ] 6.5 Пользователь **вне** whitelist: любое сообщение → вежливый отказ, БД не создаётся.

## 7. Надёжность 24/7 (issue #5, «на боевом хосте»)

- [ ] 7.1 Ежедневный бэкап в cron (пример):
      `0 3 * * * docker compose exec -T bot python scripts/backup.py /app/data/backups >> /var/log/secretary-backup.log 2>&1`
      и retention 7 дней:
      `10 3 * * * find /app/data/backups -mindepth 1 -maxdepth 1 -type d -mtime +7 -exec rm -rf {} +`
      → каталог снапшота `<UTC-метка>/` с `bot.db`, `users/*.db`, `secret.key`; права 0700/0600; снапшоты 7 дней копятся.
- [ ] 7.2 Снапшоты копируются **на другой носитель** (rsync/каплик) — копия видна и читается.
- [ ] 7.3 Перезапуск контейнера (`docker restart`) с активными незапущенными напоминаниями → после рестарта напоминания **доставлены**, события в `/list` на месте.
- [ ] 7.4 Неподтверждённая карточка (нажали «Изменить» и бросили) после рестарта → «Черновик потерялся» (ожидаемое: FSM в памяти) — и **без ошибок** в логах.
- [ ] 7.5 Длинный простой: остановить бота на 30–60 минут (или дольше созревания напоминаний) → после запуска созревшие напоминания пришли **каждому владельцу по одному разу** (дублей нет; at-least-once дубль возможен только при «крахе» между отправкой и отметкой — дефектом не считается, задокументировано).
- [ ] 7.6 `kill -9` контейнера → бот поднимается, данные целы, напоминания не потеряны.
- [ ] 7.7 **Восстановление**: остановите бота; из снапшота верните `bot.db`, `users/*.db`, `secret.key` на прежние пути (на тестовом хосте/каталоге); запустите → `/list`, `/stats` и содержимое напоминаний совпадают с состоянием на момент бэкапа.

## 8. Устойчивость к сбоям AI/сети

- [ ] 8.1 LLM недоступен (неверный `LLM_API_KEY`) → вежливое «AI-модуль недоступен» + событие всё равно создаётся локальным парсером, если текст простой («встреча завтра в 15:00»).
- [ ] 8.2 LLM отвечает >25 с → таймаут, вежливый отказ, бот жив, следующие сообщения обрабатываются.
- [ ] 8.3 Обрыв сети хоста на 5–10 мин → polling возобновился сам, ничего не «потерялось» (обновления Telegram после обрыва дошли или осознанно потеряны — зафиксировать поведение).

## 9. Инцидент LLM (issue #4, воспроизведение)

- [ ] 9.1 Пришлите **то же исходное сообщение**, что вызвало инцидент, и сравните: карточка предпросмотра vs старые `cards/*.ics` (даты/длительность/повторы/заголовки). Расхождения — зафиксировать и решить (исправить парсер/промпт либо задокументировать поведение).

## 10. Безопасность (живая проверка)

- [ ] 10.1 Внешний пользователь (не в whitelist): DM → отказ; повторные сообщения — отказ, логов ошибок не скапливается.
- [ ] 10.2 Секреты: в логах/ответах нет `BOT_TOKEN`, LLM-ключей, `ENCRYPTION_KEY`; в репозитории секретов нет.
- [ ] 10.3 Бэкап содержит личные данные → каталог бэкапов не публикуется, доступ ограничен (права на хосте).
